# Disconnect SQLite lock diagnosis (2026-10-24)

Material finding: application cancellation cleanup is not safe when disconnect interrupts an active SQLite SELECT. This is independently reproducible without prior tests, a model, a listening server, or any owner database. It is not evidence that the last reader grammar change caused the defect.

## Application boundary and cause

- `apps/api/tests/test_connected_contract.py:796-848` runs the real ASGI middleware/stream route with ASGI 2.3, a per-test file SQLite database, deterministic embeddings and lexical source extraction. It disconnects after receiving a first token and requires saved outcome `interrupted`, answer null. The generated fixture data is independent and disposable.
- `apps/api/app/api/queries.py:320-325` rechecks `present_query` before each subsequent token. `connected_query.py:82-88` executes the authorization SELECT through the request session. This live read is a valid disconnect boundary.
- The stream catches CancelledError at `queries.py:342-345`, then shields `fail_query`. `connected_query.py:612-633` rolls back, fetches the committed query identity and commits interrupted status. That shield begins after the SELECT has already been canceled.
- A deterministic scratch checkpoint waits after native `SELECT documents.id ...` execute, before SQLAlchemy fetchall, then lets the client's receive return http.disconnect. Trace proves that canceled connection is closed and a different connection issues the cleanup UPDATE; its COMMIT fails with `database is locked`.
- A paired scratch control performs exactly the same checkpoint but explicitly closes only the canceled native cursor under an AnyIO shield before rethrowing cancellation. The original outcome assertion passes. Native tracing without the checkpoint also passed, with cancellation during cursor creation rather than executing an active SELECT. This localizes the difference to the outstanding cursor/read lock, rather than a separate request or a suite-order leak.
- Installed SQLAlchemy 2.1.6 / aiosqlite 0.22.1 cancellation path terminates/closes the connection; that is not sufficient to release this interrupted cursor's SQLite lock before cleanup commits. SQLite 3.53.1, Python3.12.14, Starlette1.9.0, FastAPI0.162.0, AnyIO4.15.1, pytest9.1.1, pytest-asyncio1.4.0. The production AsyncDatabaseManager has no WAL setup either; fixture engine differences do not explain away the valid SQLite app boundary. Other database engines and installed dependency combinations were not tested.

## Recommendation and limits

Repair the application cancellation/resource-lifecycle boundary rather than xfail, increase sleeps/timeouts, retry COMMIT indiscriminately, or assume suite interference. Existing test is a valid app regression. Retain a deterministic event-gated test for disconnect while SQL is active, plus disconnect while generator is at a yield/send boundary. Ensure resource closure completes under cancellation shielding and final interrupted persistence is owned by a lifecycle that runs even when the body generator is abandoned. A broad shield around presentation alone was insufficient in the diagnostic, so do not treat it as a proved fix. The cursor-close monkeypatch is causal evidence, not a proposed production driver-private API patch.

A retry/new session alone cannot resolve a read cursor still holding a lock; this probe already used a different cleanup connection. WAL-only masking and broad noncancellable model execution were not tested or recommended. No new model/quality result, no PostgreSQL claim, and no claim every arbitrary transport cancellation schedule is covered. ASGI2.4/send-error behavior is a separate unverified boundary.
